## What this proves

- AuroraOSS dispenser accepts requests from `chrome-extension://` origin **iff** the `User-Agent` is rewritten to the Aurora client UA and `Origin` is stripped — both done via `declarativeNetRequest` modify-headers rule.
- Play API `/fdfe/*` accepts `X-DFE-*` custom headers from a fetch initiated by an MV3 service worker, **iff** the `User-Agent` is rewritten to a real Android-Finsky UA and `Origin` is stripped — same DNR mechanism.
- The hand-rolled protobuf decoder correctly parses real `ResponseWrapper` payloads from both `/details` and `/delivery` endpoints.
- `chrome.downloads.download` + per-URL `declarativeNetRequest.modifyHeaders` Cookie rule actually authenticates against `play.googleapis.com`'s APK CDN — bytes flow from Google to disk without the extension ever holding them in memory.
- The extension service worker is the only network-touching component; the page (`index.html`) does no network at all.

## Caveats

- **Filenames in Termux Chromium**: under CDP `Browser.setDownloadBehavior`, Chrome saves with the URL-derived token name instead of our `filename: 'gplaydl/<pkg>-<vc>/base.apk'` suggestion. In a real (non-CDP) browser the `filename` parameter should be honored — verify on the user's real Chrome before shipping. Tracked in `port-spec.md`.
- **Base APK timeout**: 113 MB doesn't finish in 90 s from the Termux device's network. Real desktop users will see it complete in seconds.
- **No Cloudflare bot solve**: AuroraOSS sometimes serves a JS challenge to suspicious clients. In our runs the dispenser served direct JSON to the DNR-modified request. If they tighten Cloudflare rules, we'd need a workaround.
